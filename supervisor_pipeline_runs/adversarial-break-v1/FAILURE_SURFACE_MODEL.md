# FAILURE_SURFACE_MODEL.md

Adversarial map of how two agents localise faults in the displaced-chain Defects4J variants, synthesised from seven trajectory-mining reports. This document is about how to make the top-1 wrong, not about whether the benchmark is fair. Where a harness defect shaped behaviour it is recorded because it is part of the surface, not as a caveat.

Corpus covered by the reports: ~94 runs.
- GPT-5.6 (`mini-swe-agent-openai-gpt-5-6`, diagnostic-noncanonical-v3 + hypothesis-ambiguity-v1): 15 control runs (CONVERSION-LONG-CONTROL-01, CHART-PIE-CONTROL-03, CMP-LAYOUT-CONTROL-02 x5), 35 five-hop treatment runs (CONVERSION-LONG-TREATMENT-01, CMP-LAYOUT-TREATMENT-02, CHART-PIE-TREATMENT-03, JKC-SURR-TREATMENT-04, CMP-ALIGN-TREATMENT-06 x5; MATH-NORM-TREATMENT-01 x10), LANG-CONV-CAMOUFLAGE-LOW run-001, HA-HIGH-01 run-001..005, HA-LOW-01 run-004..005.
- Claude Opus 5.5 (`mini-swe-claude`, anthropic-pilot-v1): 24 main runs (CHART-PIE/CMP-LAYOUT/CONVERSION-LONG control+treatment, LANG-CONV-CAMOUFLAGE-HIGH/LOW, x3) + 12 pre-hardening runs.

Scoreboard (wrong top-1 only):
- GPT-5.6: `CHART-PIE-TREATMENT-03` run-001..005 gold rank 6 (5/5); `CMP-LAYOUT-TREATMENT-02` run-004 gold rank 3. Plus 6/10 `MATH-NORM-TREATMENT-01` runs (001,003,004,005,006,007) timed out with no ranking. Every other completed run: rank 1.
- Claude: `CHART-PIE-TREATMENT-03` main run-001/002/003 gold rank 3/6/6, pre-hardening run-001/002 rank 6/6 (5/5 wrong). Every other run (31/36): rank 1.

Two channel confounds that are load-bearing for everything below:
1. No run of either model ever received a stack trace with a production frame. GPT's prompt "stack trace" block held only the d4j summary (`Failing tests: 1 / - <id> / Running ant ... OK`); Claude's held literally `(not provided)` (run_manifest `evidence.compliance.ok=false`, "Agent-visible failure evidence is empty", 36/36).
2. Claude could never execute a test: all 9 `defects4j test` attempts across 36 runs died with `Can't locate String/Interpolate.pm in @INC ... framework/core/Utils.pm line 45` and were never retried. GPT ran `defects4j test` in step 1 of every run and recovered expected/actual from the workspace file `failing_tests` in most runs. So "Claude ignores runtime evidence" is partly harness-induced; "Claude reaches the same top-1 as GPT without runtime evidence" is not.

## 2. Observed failure mechanisms

### M1. Compensating-pair split with contract-coherent mutated leaf (the only mechanism that beat both models every time)

**What happened.** Original `PiePlot.getArcBounds` contained a compensating pair: `deltaX = (point1.getX() - point2.getX()) * explodePercent` then `unexploded.getX() - deltaX`. The chain generator put the first negation in H3 `PlotUtilities.drift` (`double dx = point1.getX() - point2.getX();` with H1 deriving `point1` from `unexploded` and H2 deriving `point2` from `exploded`) and the second in H5 `ShapeUtilities.shift`, then mutated H5 `-` -> `+` (`double x = area.getX() + deltaX;`). A sign flip at drift, nudge, shift or the facade all pass the test; the fault is under-determined by the test. Every run broke the tie by asking whose body disagrees with its own name/contract. H5's mutated body is the textbook `shift(area, dx, dy)`; H3's un-mutated body reads `unexploded - exploded`, the reverse of the "natural" direction for an explosion displacement. Both models blamed H3 and exonerated H5.

**Evidence.**
- `mini-swe-agent-openai-gpt-5-6__CHART-PIE-TREATMENT-03__run-001` E: "PlotUtilities.drift computes dx and dy as point1 minus point2, then Plot.nudge adds that displacement" -> "Reversing the point-difference direction yields both expected coordinate pairs; this is the most specific faulty method." On gold: "ShapeUtilities.shift preserves width and height and adds the supplied deltas ... exposing any upstream sign error" -> "It is a lower-probability direct callee in the geometry chain."
- `...__CHART-PIE-TREATMENT-03__run-005` E: "Plot.nudge only scales the supplied displacement and ShapeUtilities.shift adds it while preserving width and height; ... their observed operations are internally consistent."
- `mini-swe-claude__CHART-PIE-TREATMENT-03__run-001` [hardened]: "drift's Javadoc describes the displacement from the unexploded point to the exploded point, i.e. p2-p1, so drift most likely has the reversed subtraction. shift simply adds the displacement, which matches its documentation."
- `mini-swe-claude__CHART-PIE-TREATMENT-03__run-003` [hardened]: "drift computes dx = point1.x - point2.x (unexploded - exploded); test expects shift (50-100)*0.25 = -12.5 giving x=87.5" -> "Sign of offset reversed in drift".
- `pre:mini-swe-claude__CHART-PIE-TREATMENT-03__run-002`: "Worked by hand: at angle 180, point1=(100,200) and point2=(50,200), so dx=+50. Multiplying by 0.25 gives x=112.5, but the test expects 87.5. So the direction is reversed and should be point2 - point1."
- The prior exists in the single-method control where it cannot matter: `mini-swe-claude__CHART-PIE-CONTROL-03__run-003` "point1 - point2 should be point2 - point1" vs run-001 "deltaX and deltaY should be subtracted". The chain turns an indifferent choice of expression into a wrong choice of method.
- The drift Javadoc actually seen is directionless: "Computes the drift between a point on the unexploded ring and the corresponding point on the exploded ring".
- Frequency: 10/10 runs (GPT 5/5, Claude 3 hardened + 2 pre-hardening) rank drift 1; gold rank 6 in 9/10, rank 3 in 1/10 (Claude hardened run-001). Top-1 identical whether or not the assertion message was seen (4 saw it, 6 did not).

Note: report 3 states that CHART-PIE-03 pair_config says no GPT-5.6 runs were performed on this bug; reports 1 and 7 examined five GPT runs on it. The pair_config note is stale.

### M2. Direction-loaded identifiers alone suffice (no Javadoc needed)

4/5 Claude CHART runs (hardened 002, 003; pre 001, 002) never displayed any Javadoc description sentence yet blamed drift, deriving direction from `arc1 = new Arc2D.Double(unexploded, ...)` -> `point1`, `arc2 = new Arc2D.Double(exploded, ...)` -> `point2`, `point1 - point2`. Evidence: `mini-swe-claude__CHART-PIE-TREATMENT-03__run-003` msg#9 shows only lines 89-98 of PlotUtilities.java (`* @return The bounds of the exploded section.` / `*/` / body). GPT runs cannot separate the two because they always saw Javadoc. Model specificity: demonstrated for Claude; the Javadoc, when read, only reinforces.

### M3. Generic-utility exoneration below arithmetic-free glue

Once `shift` was judged "internally consistent" it was ranked not just below drift but below hops that do no arithmetic on the offset (H1 ring/H2 rim compute arc endpoints; the facade only guards `explodePercent == 0.0`). GPT: shift rank 6 of 6 in 5/5; ranks 3-5 are permutations of ring/rim/nudge; rank 2 always the facade. Claude: shift rank 6 in 4/5 (order drift, nudge, rim, ring, getArcBounds, shift). Both checked callers and found each hop single-use (`GPT run-005: grep -R "ShapeUtilities.shift" -n source tests` -> one caller `Plot.java:1566`; `Claude hardened run-001: grep -rn "\.shift(\|nudge(\|drift(\|\.rim(\|\.ring(" source | grep -v "public static"` -> one call site per hop), so no cross-check was possible. This is why hit@5 also fails.

### M4. Facade promotion when leaf attribution is not decisive (use-site fix availability)

`mini-swe-agent-openai-gpt-5-6__CMP-LAYOUT-TREATMENT-02__run-004`: gold `ZipArchiveInputStream.flagOffset` rank 3; facade `parseTarHeader` rank 1; H4 `checksumBoundary` rank 2. The facade keeps a correct running offset (`offset += CHKSUMLEN;` -> 156) and then ignores it: `final int flagPos = CpioArchiveEntry.identityWidth(...); linkFlag = header[flagPos]; offset++;` (msg 12, `sed -n '280,760p'`). Run-004 alone resolved the ambiguity toward the method where the one-line repair (`header[offset]`) is visible: E "parseTarHeader reads a checksum byte instead of the type flag; it is the direct and strongest fault candidate." Nothing in run-004's command sequence is missing relative to runs 002/003/005: it read the facade, all five hops (msgs 18, 20, 24, 28, 32), computed `print(100+8+8+8+12+12)` -> 148 (msg 29), had the gold body on screen one step before submitting (msg 32: `80- final int afterChecksum = numericEnd; 81- return afterChecksum;`). The flip is a judgement at submission. Run-003 recorded the same observation ("its ordinary offset variable is already 156 at that point") and still chose the leaf. The pair_config itself lists `linkFlag = header[flagPos + CHKSUMLEN];` as a legitimate facade-side ownership candidate. Frequency: 1/5 GPT, 0/3 Claude; but Claude ranked the facade 2 in 3/3 CMP-LAYOUT-TREATMENT runs with `candidate_methods ['ZipArchiveInputStream.flagOffset', 'TarArchiveEntry.parseTarHeader']`.

### M5. Name-absorbed blame: the hop named for the missing operation takes the credit

Run-004 E3: "checksumBoundary ultimately returns numericEnd unchanged, omitting the eight-byte TAR checksum field" — the method that literally returns numericEnd unchanged is flagOffset. H4's body only range-checks and forwards (msg 28: `if (numericEnd < 0) throw ...; return ZipArchiveInputStream.flagOffset(numericEnd);`), but its Javadoc "Validates the end of the numeric fields of a header record and hands it to the field that follows them" claims the boundary. H4 was co-candidate in 3/5 GPT CMP runs (run-001 E2, run-004 E3, run-005 E3) and rank 2 or 3 in 8/8 runs — always the gold's nearest competitor. The project's own OWNERSHIP_UNIQUENESS_AUDIT.md pre-flagged this exact caveat.

### M6. Leaf rank-1 in CMP-LAYOUT rests on generator confession cues, not arithmetic

Three lexical tells in the gold: local `afterChecksum` that contradicts its own value (seen 8/8, cited 7/8), Javadoc "Returns the offset of the type flag" (identical promise on every hop: run-003 msg 29 shows `@return the offset of the type flag within the record` at ArArchiveEntry.java:91, ArArchiveInputStream.java:159, CpioArchiveInputStream.java:458, CpioArchiveEntry.java:705), and an unused `import static org.apache.commons.compress.archivers.tar.TarConstants.CHKSUMLEN;` at line 21 of ZipArchiveInputStream.java — seen by exactly one run (`...__CMP-LAYOUT-TREATMENT-02__run-001` msg 37 via `sed -n '1,100p'`) and cited as decisive: "the unused checksum-width import directly indicates the missing layout adjustment." Runs 002/003/004/005 used `grep -B10..-C20` or `sed 55,95` and never saw the import; run-004 (`-B10`, lines 69-83) had the narrowest view and is the run that flipped. The margin between rank 1 and rank 3 here is a single local-variable name.

### M7. Facade anchoring at rank 2 (GPT) is a "what the test names" prior, not a call-graph position

Facade rank 2 in 16/29 completed GPT treatment runs and rank 3 in 4 (MATH-NORM), even when the facade is a guard plus delegate (`if (explodePercent == 0.0) return unexploded; else return CompassPlot.ring(...)`). It drops to rank 6 in 5/5 JKC runs where the test calls `UTF8Writer.write`, not `convertSurrogate`. In the one wavering run (CMP run-004) the facade took rank 1. ## 5. Brief behaviours, answered

**Found gold but ranked another higher.** YES. Every one of 10 CHART-PIE-TREATMENT-03 runs displayed shift's body (`double x = area.getX() + deltaX;`) and ranked it 6 (9/10) or 3 (1/10). `mini-swe-agent-openai-gpt-5-6__CMP-LAYOUT-TREATMENT-02__run-004` had `80- final int afterChecksum = numericEnd; 81- return afterChecksum;` on screen (msg 32) one step before ranking it 3. Claude hardened CHART run-001 listed shift in `candidate_methods` and ranked it 3.

**Inspected the right region but wrong causal story.** YES, four kinds. (a) Correct arithmetic, wrong owner: all 10 CHART runs reconstruct 112.5 vs 87.5 and the full 6-method chain, then assign the sign to drift. (b) Chain-tail conflation: run-004 CMP "checksumBoundary ultimately returns numericEnd unchanged" (it is flagOffset that does). (c) Over-predicted scope: `mini-swe-claude__CMP-LAYOUT-CONTROL-02__run-001` "every later field is off by one byte" (false; 157 is correct) with parseName ranked 3-5 as a result. **Stopped too early.** YES for Claude: submit 0 calls after first seeing the gold declaration in 16/36 runs, 1 call in 16/36; hand-simulates only the first assertion (0/5 CHART chains mention 117.677); never retried the failed test (9/9); CHART treatments done in 7 calls / 30 s. **Trusted names/comments.** YES, and it is the primary decision procedure when the test under-determines the fault. Names: `drift` owns the displacement; `shift` "matches its documentation" (Claude run-001); "internally consistent" (GPT run-005); `checksumBoundary` owns the checksum (run-004 rank 2); `afterChecksum` decides 7/8 CMP-LAYOUT hits; `flagOffset`'s Javadoc "Returns the offset of the type flag" cited as the promise violated. **Followed a misleading caller/callee.** NO misleading edge existed in any variant (every chain is a linear single-use static path and every run traversed it correctly). ## 6. Build priorities

1. **Replicate L1 on new bugs** (compensating pair split; mutated leaf textbook-for-its-name; direction-loaded identifiers upstream; single-use hops; value-type mutation; assertion in test body). Expected wrong top-1 for both models, deterministic.
2. **Amplify L2 on CMP-LAYOUT** (strip `afterChecksum` and the import, rename H4 to the missing operation, keep `offset += CHKSUMLEN` beside the call with a hint comment). Expect GPT flip rate to rise from 1/5 toward systematic and Claude's facade rank 2 to become rank 1.
3. **Build one L3 variant** (interface/registry/static-initializer dispatch). If it behaves as predicted, hit@10 = 0 for both models regardless of reasoning.
4. **Build one L4 variant** (passing test pinning the buggy producer). Tests are currently ignored as refuters; a test that documents the bug as intended should flip GPT's contract inference.
5. **Pair any of the above with L6** (remove sibling oracle) and, for Claude, L7/L8 (single-method-named test, first-assertion ambiguity). For hit@k, add L12 (chain length 10+).

Everything else (L9-L11, L13-L18) is second-order: it raises cost or variance but has not been observed to move rank 1 on its own.
