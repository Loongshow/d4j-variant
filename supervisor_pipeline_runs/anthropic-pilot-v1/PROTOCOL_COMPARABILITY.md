# Protocol comparability: GPT-5.6 versus Claude (Phase 4)

## Verdict: NEAR_EQUIVALENT

Every element of the measurement protocol is byte-identical across the two models. What differs is the
model and provider themselves, the server process that hosts the run, and one measured consequence of
Claude's different shell idiom. Nothing that determines what the agent is asked, what it can do, how long
it has, or how it is scored differs.

FULL was not claimed, for the three reasons listed under "Residual differences" below. NOT_COMPARABLE does
not apply, so the pilot was allowed to proceed.

## Residual differences, and why each is acceptable

1. **Different server process and repository root.** The Claude runs execute on a patched copy of the
   harness at a different port with its own `benchmark_runs` tree. This was deliberate: it keeps the frozen
   GPT-5.6 tree byte-identical (verified: all 32 `.mjs` files unchanged) and keeps the frozen run artifacts
   untouched (4003 artifact hashes re-verified). The copy differs from the frozen tree in exactly two files
   and 4 edits, none of which is on an OpenAI code path; the variant packages are reached read-only through
   a symlink to the frozen root, so both models score the same bytes.
2. **The pilot server has no OpenAI credential.** It cannot execute an OpenAI run at all, which is a safety
   property rather than a comparability problem, but it does mean the two models were not run by the same
   process.
3. **Claude's shell idiom defeats one harness-side counter.** Claude writes `f=<path>; sed -n ... "$f"`
   style commands, so the harness's own `unique_files_read` field reports 0 even when files were read. This
   is a counting artifact, not a capability difference: the trajectory shows the reads and the greps. All
   comparative metrics in this pilot are therefore computed by one provider-independent script from the raw
   commands (`scripts/pilot_run_metrics.py`), applied identically to both models' trajectories, and the
   harness-side `unique_files_read` field is not used in any comparison.

4. **Anthropic prompt caching is switched on automatically for Claude and had no equivalent for GPT-5.6.**
   `minisweagent/models/__init__.py:56` enables `set_cache_control="default_end"` whenever the model name
   contains `anthropic`, `claude`, `opus` or `sonnet`. This is inside the installed agent package, which is
   deliberately not modified, so Claude runs benefit from cache reads that the GPT-5.6 runs never had. It
   changes cost and latency, not the prompt content, the tools, the budget or the scoring. Cost comparisons
   between the two models are therefore reported as measured spend with this difference stated, never as a
   claim about which model is intrinsically cheaper per task.
5. **The provider endpoint was pinned rather than inherited.** The audit found that the parent shell exports
   `ANTHROPIC_BASE_URL`. Its value was checked to be exactly `https://api.anthropic.com` with no path and no
   query, i.e. the official endpoint, and the shell carries no `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN`
   at all, so the only credential available to the pilot server was the authorized key from the benchmark
   area's own env file. The pilot launcher now pins `ANTHROPIC_BASE_URL` to the official endpoint explicitly
   and clears every Claude Code auth variable before starting the server, so provenance cannot be ambiguous.
   The 12 runs made before this hardening are preserved under `pre_hardening/` and are excluded from every
   results table.

6. **litellm injects `max_tokens` for Anthropic and nothing for OpenAI.** Measured, without an API call:
   `AnthropicConfig.transform_request` fills `max_tokens: 128000` (the model's full max output) when the
   caller supplies none, while the OpenAI arm sends no `max_tokens` at all. An adversarial check raised the
   possibility that a request this large would be refused with "streaming is required", which would have made
   the Anthropic arm unrunnable; **that did not happen** - every pilot run was accepted and completed, so the
   concern is recorded as falsified for `claude-opus-5-5` on this endpoint rather than left open. The value is
   a ceiling, not a target, and it cannot be equalised without editing the frozen GPT-5.6 run config, because
   the Anthropic API requires the field.
7. **A provider failure on the Claude arm may be recorded as `timeout` rather than `provider_error`.**
   `minisweagent/models/litellm_model.py` does not abort on `BadRequestError`, `RateLimitError`,
   `InternalServerError` or `APIConnectionError`, so the agent retries with exponential backoff that can
   exceed the harness's 300 s SIGTERM, and the harness checks `timed_out` first. No run in this pilot failed,
   so the distinction never had to be drawn, but any future Anthropic block should read the preserved
   `raw_agent_output.txt` of a `timeout` run before calling it a timeout.

## What was verified empirically, not assumed

- A real Claude run's `run_manifest.json` reports prompt version and base hash, budget and timeouts
  identical to the frozen protocol, and `protocol_identity_ok` is asserted per run by
  `scripts/post_run_check_claude.py` against a hard-coded expected tuple.
- The ranking parser accepted Claude's submission and produced a scored `gold_rank`.
- `source_integrity.json` reports `ok: true`, so Claude did not modify repository source.
- The out-of-workspace scanner found no run reading another run's results.
